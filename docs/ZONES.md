# Zones: format, pipeline, dungeons and travel

Every zone is one file, `content/zones/<id>.json`. Adding a zone is adding a file (and, for a
hand-authored one, a Godot scene). No code changes.

## Kinds

| kind | what it is | where its geometry comes from |
|---|---|---|
| `hub` | a safe starting city (bank, vendors, trainers, bind point) | a hand-authored Godot scene, `client/zones/<id>.tscn` |
| `outdoor` | wilds with terrain, props and camps | the zone file (written by `tools/gen_world.py`) |
| `dungeon` | rooms and corridors | a seed in the zone file; server and client generate the same layout |
| `test` | The Proving Flats, the development plain | the zone file; never reachable by zone lines |

## The zone file

```json
{
  "id": "emberglade", "name": "The Emberglade", "kind": "outdoor",
  "levels": {"min": 1, "max": 8},
  "bounds": {"min_x": -400, "min_z": -400, "max_x": 400, "max_z": 400},
  "terrain": {"base": 0, "hills": [[x, z, radius, height], ...]},
  "safe_spawn": {"x": -370, "y": 0, "z": 0, "yaw": -1.5708},
  "scene": "res://zones/emberhold.tscn",          // hubs: the client scene (its export is merged in)
  "dungeon": {"seed": 4242, "rooms": 9, "cell": 4}, // dungeons instead of bounds
  "props": [{"prop": "tree_oak", "x": .., "z": .., "yaw": ..}],  // what the client draws
  "obstacles": [{"x": .., "z": .., "radius": ..}],   // round blockers (server collision + line of sight)
  "walls": [{"x": .., "z": .., "hx": .., "hz": .., "yaw": ..}],  // box blockers
  "entries": [{"id": "emberhold_road", "x": .., "z": .., "yaw": ..}],  // arrival points
  "zone_lines": [{"id": "to_emberhold", "x": .., "z": .., "hx": .., "hz": .., "to": "emberhold", "entry": "east_gate"}],
  "spawns": [{"mob": "ember_rat", "x": .., "z": .., "count": 5, "radius": 14}],
  "theme": {"biome": "meadow", "ground": "#5d7a3e", "sky": "#5a7fb5", "fog": "#c4c9b0"}
}
```

- **Terrain** is the base height plus round hills: `height * (1 - (d/radius)^2)^2` inside each
  hill's radius. Every entity's height comes from it (server `Terrain::height`, client
  `zone_geom.gd height()`).
- **Collision** is 2D: circles, boxes rotated about their centre, and (dungeons) wall tiles. A body
  (players 0.4 m, mobs 0.5 m) is pushed out of circles, then boxes, then tiles, twice per step. The
  server (`game/world_geom.cpp`) and the client's prediction (`client/scripts/world/zone_geom.gd`)
  run the same rule on the same lists, so walking into a wall slides along it on both sides with no
  corrections. Line of sight for spells uses the same shapes.
- **Zone lines** are trigger boxes. Standing in one (alive, at least 1 s after arriving) moves you to
  the named entry of the target zone. Entries must not lie inside a zone line (no bouncing).
- **Dungeon rooms** stand in for coordinates: spawns, entries and zone lines may name a `room`
  (`entrance`, `boss`, `all` for spawns, or an index). They are placed when the content loads.
- `levels` is the zone's band; `persistent` (default: hubs and the test zone) keeps it loaded when
  empty. `raid: true` (Phase 15) marks a raid dungeon: only a raid takes its zone lines in, and its
  bosses lock raiders out of their treasure (`social.raid.lockout_hours`).

## The pipeline: scenes to server collision

A hand-authored zone is a Godot scene. The scene is the one source of truth; the server's collision,
markers and zone lines are **exported** from it:

```
client/zones/emberhold.tscn  --(client/tools/export_zones.gd)-->  content/zones/scenes/emberhold.json
                                                                   (walls, obstacles, zone_lines, entries, npcs, spawns)
content/zones/emberhold.json + scenes/emberhold.json  --(server load)-->  collision map + nav grid + markers
                                                      --(tools/sync_client_content.py)-->  client/data/zones/emberhold.json
```

What the exporter reads from a scene:

| node | becomes |
|---|---|
| `StaticBody3D` > `CollisionShape3D` with a `BoxShape3D` | a wall (centre, half extents, yaw) |
| `StaticBody3D` > `CollisionShape3D` with a `CylinderShape3D` | an obstacle (centre, radius) |
| `Area3D` with metadata `kind = "zone_line"`, `id`, `to`, `entry`, holding a `BoxShape3D` | a zone line |
| `Marker3D` with metadata `kind = "entry"`, `id` | an entry (position and yaw) |
| `Marker3D` with metadata `kind = "npc"`, `id` | where an `npcs.json` NPC stands (overrides its x/z/yaw) |
| `Marker3D` with metadata `kind = "spawn"`, `mob`, `count`, `radius` | a spawn group |

Props (`client/zones/props/*.tscn`, generated by `tools/world_props.py` from primitives) carry their
own `StaticBody3D` shapes, so placing a house in a scene is all it takes for the server to collide
with it. `tools/gen_world.py` scatters the same props over outdoor zones and writes their collision
from the same table.

Commands:

```
python3 tools/world_props.py                       # prop scenes (CI: --check)
python3 tools/gen_world.py                         # outdoor/dungeon zone files and world NPCs (CI: --check)
godot --headless --path client --import
godot --headless --path client --script res://tools/export_zones.gd   # scene exports (CI: -- --check)
python3 tools/sync_client_content.py               # the client's copy (CI: --check)
```

**Navigation:** the server derives a walkability grid (`game/nav_grid.cpp`, 2 m cells by default,
`nav_cell` per zone) from the same collision when the zone loads, by rasterizing each shape grown by
a mob's body. Mobs walk straight when the way is clear and follow a bounded A* path (smoothed by
string pulling) when it is not. Path searches are budgeted per tick.

**Checks that the two sides agree:** the server computes a **layout hash** of each zone's geometry
(bounds, terrain, shapes, and the dungeon layout) and sends it in `EnterWorldResult`; the client
computes the same hash from its bundled copy and warns ("please update your client") on a mismatch.
The dungeon generator is pinned by a golden hash in both the C++ and the GDScript tests.

## Procedural dungeons

`dungeon_gen.cpp` / `dungeon_gen.gd` (integer math only, xorshift32):

1. A grid of `(g+1) x (g+1)` sectors (`g*g >= rooms`). The entrance takes the bottom-middle sector;
   each step attaches a random free neighbour of a placed sector, growing a tree.
2. One room per sector (sides `min_room..max_room` tiles, placed randomly inside it). The deepest
   room (first on ties) is the boss room and fills its sector.
3. An L-shaped corridor (`corridor` tiles wide) from each room to its parent, horizontal or vertical
   leg first.

The server sends the seed in `EnterWorldResult`; the client builds floor and wall tiles from it
(MultiMesh) and a brazier in every room. The entrance room holds the exit line and the arrival entry.

## Zone changes and instances

- Zones load on demand (hubs and the test zone at start) and unload after
  `zone_idle_seconds` (config, default 300) with no players and no player corpses.
- Leaving a zone: the zone queues a transfer (zone line, travel, a portal or gate spell, a respawn at
  a bind point elsewhere). After the zones' tick, the game server snapshots the character, removes it,
  adds it to the destination at the entry, sends a new `EnterWorldResult` (`zone_change = true`)
  and the initial state, and saves the character (with everyone else's pending changes, in one
  transaction). A summoned pet follows with its health; a charm breaks; a trade is cancelled.
- The client swaps in a new world scene for the new zone, shows a zone banner, and keeps playing.

## Travel

- **Soulbinders** (`role: binder`, one option `bind`) set your bind point where you stand.
- **Waystone keepers** (`role: teleporter`) move you to a city or travel point for a fee.
- **Ferries** (`role: ferry`) take your fare when they sail: you board, and if you are still on the
  dock after `delay` seconds you cross.
- **Portal spells:** a teleport effect's destination may be `bind`, `safe_spot`, a city id, or a
  travel point id (`content/travel.json`), in any zone. Druid and Wizard portals use them.

## Mobs, specials and bosses

Mobs are generated by `tools/gen_mobs.py` (families with level tiers, dungeon trash, named rares, bosses)
into `content/mobs.json`; anything they cast is in `content/mob_spells.json`. A mob's `specials`:

| type | fields | what it does |
|---|---|---|
| `proc` | `effect`, `chance` | a landed melee hit casts the effect on the target |
| `cast` | `effect`, `every`, `range` | every few seconds in a fight, at the target (line of sight) |
| `aoe` | `effect`, `every`, `range`, `center` | everyone within `range` of the target (`target`, default: spread out) or of the mob (`self`: step back) |
| `enrage` | `below`, `value` | below that health fraction, +`value`% melee damage |
| `enrage_timer` | `seconds`, `value` | after that long fighting, +`value`% melee damage |
| `rampage` | `chance` | a landed hit also strikes another foe in reach |
| `summon` | `every`, `range` | a target farther than `range` is pulled back to the mob |
| `adds` | `at`, `mob`, `count` | at each health fraction in `at`, `count` of `mob` join the fight (they leave if the boss resets) |

Each may carry a `message` the mob says aloud. A dungeon spawn may name a `rare` (a named mob) and
`rare_chance`: a respawn is the rare that often, one at a time. Bosses are `boss` and `named`; their
loot tables (built by `tools/gen_items.py`) carry their dungeon's named items.
